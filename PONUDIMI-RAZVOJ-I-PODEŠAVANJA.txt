3. TRENUTNA TEHNIČKA ARHITEKTURA
===============================================================================

3.1. Frontend

Glavne tehnologije:
- React 19
- TanStack Start / TanStack Router
- Vite
- Nitro, preset node-server
- Tailwind CSS 4
- TypeScript
- Node.js najmanje 22.12 prema package.json

Glavne putanje:
- package.json — skripte, zavisnosti i Node zahtev
- vite.config.ts — frontend build i Nitro proxy pravila
- src/routes/ — stranice platforme
- src/components/ — zajedničke komponente
- src/styles.css — boje, raspored i responsive pravila
- src/integrations/standalone/client.ts — veza browsera sa samostalnim API-jem
- public/ — javni resursi, manifest i PWA elementi

Skripte u glavnom package.json:
- npm run dev — razvojni Vite server
- npm run build — produkcioni build
- npm run preview — lokalni pregled build-a
- npm run lint — ESLint
- npm start — pokretanje .output/server/index.mjs
- prebuild — automatski pokreće npm audit pre build-a

3.2. API

Glavne putanje:
- standalone/api/server.mjs — Express API
- standalone/api/package.json — API zavisnosti i start skripta
- standalone/db/init.sql — PostgreSQL šema i dopunska inicijalizacija
- standalone/api/grant-admin.mjs — ručna dodela prve administratorske uloge
- standalone/Dockerfile.api — Docker slika API-ja

Tehnologije:
- Express 5
- PostgreSQL preko pg
- bcryptjs za hash lozinki
- jsonwebtoken za sesije
- express-rate-limit za ograničenje zahteva
- Helmet za HTTP bezbednosna zaglavlja
- Multer za upload
- Sharp za obradu fotografija
- Nodemailer za SMTP
- AWS SDK S3 klijent za S3-kompatibilno skladište
- QRCode i kriptografske funkcije za postojeću, trenutno isključenu TOTP funkcionalnost

API se pokreće komandom npm start iz standalone/api, odnosno node server.mjs.

3.3. Samostalna Docker arhitektura — planirani raspored

standalone/docker-compose.yml definiše četiri servisa:

1. db
   - PostgreSQL 17 Alpine
   - baza: ponudimi
   - korisnik baze: ponudimi
   - lozinka iz POSTGRES_PASSWORD
   - trajni Docker volumen: postgres_data
   - inicijalna SQL datoteka: standalone/db/init.sql

2. api
   - Node.js 22 Alpine
   - Express API
   - interni port 4000
   - DATABASE_URL prema db servisu
   - JWT_SECRET
   - UPLOAD_DIR=/data/uploads
   - opcionalni SMTP, Twilio, APR i S3/R2 parametri
   - Docker volumen uploads_data

3. web
   - Node.js 22 Alpine
   - izgradnja frontend aplikacije iz korena repozitorijuma
   - interni port 3000
   - start: node .output/server/index.mjs

4. caddy
   - Caddy 2 Alpine
   - javni portovi 80 i 443, uključujući UDP 443
   - automatsko HTTPS za javni domen
   - Docker volumeni caddy_data i caddy_config

Caddyfile:
- /api/* prosleđuje API servisu
- /uploads/* prosleđuje API servisu
- /sitemap.xml i /robots.txt prosleđuje API servisu
- ostale putanje prosleđuje frontend servisu

VAŽNO O STANJU DOCKER INSTALACIJE
Ovo je deklarisana arhitektura u repozitorijumu, ali kompletna Docker instalacija nije potvrđena. Pregled koda je otkrio blokirajuće neslaganje u Dockerfile.api i neslaganje u načinu na koji browser bira API adresu. Detalji su u odeljku 12. Ne tretirati ZIP kao produkciono spreman dok se te stavke ne isprave i testiraju.

3.4. Zavisnosti i ponovljivost build-a

- Glavni package.json zahteva Node >=22.12.
- Dockerfile.web koristi node:22-alpine.
- Dockerfile.api koristi node:22-alpine.
- Baza koristi postgres:17-alpine.
- Caddy koristi caddy:2-alpine.
- U repozitorijumu postoji bun.lock, ali pregledani build i Render procesi koriste npm.
- Nije pronađen package-lock.json ni za frontend ni za API. Zbog toga npm install može vremenom razrešiti drugačije verzije paketa unutar dozvoljenih semver opsega. Ovo je otvorena stavka za potpuno ponovljive build-ove.
- Glavni frontend ima prebuild skriptu koja pokreće npm audit.
- API package.json na aktivnoj API grani ima postinstall proveru npm audit --omit=dev. Build/install može stati ako audit prijavi blokirajući problem.

Opšte pravilo:
- Docker Compose čita standalone/.env.
- Render promenljive se unose u Render Dashboard > odgovarajući servis > Environment.
- Stvarne vrednosti nikada ne upisivati u GitHub, ovaj dokument ili frontend kod.
- .gitignore isključuje .env i .env.*; .env.example je dozvoljen kao šablon.
- Pri instalaciji na novom serveru generisati nove tajne, osim kada se radi kontrolisana migracija postojećeg sistema.

5.1. Obavezne za Docker samostalnu instalaciju

POSTGRES_PASSWORD
Gde: standalone/.env; Docker Compose prosleđuje PostgreSQL servisu i koristi je za DATABASE_URL API-ja.
Obavezno: DA.
Bezbedno generisanje: openssl rand -hex 32.
Promena na novom serveru: generisati novu vrednost. Ne koristiti istu lozinku na više instalacija.

JWT_SECRET
Gde: standalone/.env; API kontejner. Na Renderu: Environment API servisa.
Obavezno: DA.
Uslov koda: najmanje 32 karaktera.
Bezbedno generisanje: openssl rand -hex 48.
Promena na novom serveru: generisati novu vrednost. Promena ključa poništava postojeće JWT sesije.

ADMIN_EMAIL
Gde: standalone/.env; API kontejner; koristi ga grant-admin.mjs.
Obavezno: DA za planirani postupak prvog administratora.
Vrednost: adresa koju vlasnik platforme kontroliše. Nije lozinka, ali ne objavljivati je nepotrebno.
Promena na novom serveru: postaviti željenu administratorsku adresu pre registracije prvog admin naloga. Registracija i komanda grant-admin moraju koristiti istu adresu.

DOMAIN
Gde: standalone/.env; Caddy servis preko promenljive DOMAIN.
Obavezno: DA za javni domen; za lokalni test skripta koristi :80 ili localhost.
Primer oblika: ponudimi.example
Promena na novom serveru: uneti stvarni domen bez https:// i bez putanje. DNS mora pokazivati na server.

PUBLIC_APP_URL
Gde: standalone/.env; API koristi je za reset lozinke, email linkove, sitemap i robots.
Obavezno: DA za ispravne javne linkove; u produkciji koristiti HTTPS.
Primer oblika: https://ponudimi.example
Promena na novom serveru: uskladiti sa domenom i javnim HTTPS URL-om. Ne ostavljati http://localhost u produkciji.

DATABASE_URL
Gde: Render Environment API servisa ili okruženje Node procesa. U Docker Compose režimu sastavlja se iz POSTGRES_PASSWORD i naziva db servisa.
Obavezno: DA za API.
Tajna: DA; sadrži pristupne podatke baze.
Bezbedno generisanje: ne generisati nasumično URL; preuzeti connection string iz pouzdanog PostgreSQL provajdera ili koristiti Compose vrednost.
Promena na novom serveru: uneti adresu nove baze, korisnika, lozinku, port i naziv baze. Ne slati ovaj URL u chat ili dokument.

5.2. SMTP — email

SMTP_HOST
SMTP_PORT
SMTP_SECURE
SMTP_USER
SMTP_PASS
SMTP_FROM

Gde: standalone/.env i API kontejner; na Renderu Environment API servisa.
Obavezno: SMTP_HOST, SMTP_USER i SMTP_PASS potrebni su za slanje email poruka i funkciju oporavka lozinke.
Uobičajeni primer podešavanja: port 587 uz SMTP_SECURE=false ili port 465 uz SMTP_SECURE=true. Tačan režim potvrditi kod SMTP provajdera.
SMTP_PASS je tajna i dobija se od email provajdera; ne generisati je lokalno.
SMTP_FROM može biti verifikovana adresa pošiljaoca; ako nije uneta, kod koristi SMTP_USER.
Promena na novom serveru: koristiti nalog/SMTP kredencijale koji pripadaju novom domenu i provajderu.

Trenutna funkcionalnost:
- SMTP je potreban za zahtev za promenu lozinke.
- Email potvrda registracije postoji u API kodu kao pomoćna funkcija i endpoint, ali obavezni tok potvrde trenutno nije uključen u registraciju. Detalji u odeljku 7.
- Ako se obavezna email potvrda ponovo uključi, SMTP postaje obavezan i za registraciju.

5.3. Twilio Verify — SMS

TWILIO_ACCOUNT_SID
TWILIO_AUTH_TOKEN
TWILIO_VERIFY_SERVICE_SID

Gde: standalone/.env i API kontejner; API koristi ove vrednosti za Twilio Verify.
Obavezno: NE za trenutno aktivnu prijavu i registraciju; DA ako se ponovo uključi obavezna SMS verifikacija.
Tajne: TWILIO_AUTH_TOKEN je tajna. SID vrednosti su identifikatori naloga/servisa, ali ih takođe ne objavljivati.
Bezbedno pribavljanje: iz sopstvenog Twilio naloga i Verify Service podešavanja.
Promena na novom serveru: napraviti ili izabrati sopstveni Verify Service i uneti nove kredencijale.
Broj telefona se normalizuje na međunarodni format za Srbiju, npr. +3816xxxxxxx.

5.4. Skladištenje fotografija — lokalna baza ili S3/R2

UPLOAD_DIR
Gde: API okruženje. Docker Compose postavlja /data/uploads.
Obavezno: preporučeno definisati u Docker instalaciji.
Promena na novom serveru: koristiti putanju koja je vezana za trajni volumen, ne privremeni kontejnerski filesystem.

S3_ENDPOINT
S3_BUCKET
S3_ACCESS_KEY_ID
S3_SECRET_ACCESS_KEY
S3_REGION

Gde: standalone/.env i API kontejner; u Renderu Environment API servisa.
Obavezno: NE, samo ako se koristi S3-kompatibilno skladište kao Cloudflare R2.
Uslov koda: S3 režim se uključuje tek kada su postavljeni endpoint, bucket, access key ID i secret access key.
S3_REGION ima podrazumevanu vrednost auto.
Bezbedno pribavljanje: napraviti privatni bucket i namenski API token sa minimalnim pravima samo nad tim bucket-om.
Promena na novom serveru: ako se koristi lokalni PostgreSQL režim, ostaviti S3 promenljive prazne; ako se koristi R2, uneti novi endpoint, bucket i namenski ključ.

VAŽNO — stvarno ponašanje trenutnog API koda:
- kada S3 nije konfigurisan, saveImage čuva binarni sadržaj fotografije u PostgreSQL tabeli storage_objects, u bytea polju;
- kada je S3 kompletno konfigurisan, fotografija se čuva u S3/R2;
- tabela slike_oglasa čuva vezu sa ponudom/zahtevom, putanju i redosled;
- UPLOAD_DIR i uploads_data i dalje postoje za lokalne/legacy datoteke i statičko posluživanje;
- opis u pojedinim README/.env komentarima da se sve nove fotografije podrazumevano čuvaju na lokalnom disku nije usklađen sa trenutnim saveImage kodom. Za novi API kod podrazumevano skladište je PostgreSQL storage_objects.

5.5. Frontend/API adresa

PONUDIMI_API_ORIGIN
Gde: Vite build okruženje, koristi se u vite.config.ts za Nitro proxy pravila.
Obavezno: nije posebno označeno kao obavezno jer postoji podrazumevana Render API adresa.
Trenutna podrazumevana vrednost u vite.config.ts: https://ponudimi-test-api.onrender.com
Promena na novom serveru: treba je uskladiti sa internim API adresiranjem, ali sama promena ove promenljive trenutno nije dovoljna za browser klijenta.

API_INTERNAL_URL
Gde: web servis u standalone/docker-compose.yml; koristi se u SSR putanji standalone klijenta.
Primer u Compose konfiguraciji: http://api:4000
Obavezno: za SSR pristup API-ju u Docker mreži.
Promena na novom serveru: ako se ime API servisa ili interni port promene, promeniti i ovu vrednost.

KRITIČNO:
src/integrations/standalone/client.ts trenutno ima API_ORIGIN hardkodiran na https://ponudimi-test-api.onrender.com. Browser grana koda direktno koristi taj URL za API zahteve i javne URL-ove fotografija. Zato API_INTERNAL_URL i PONUDIMI_API_ORIGIN trenutno ne garantuju da će browser koristiti novi server. Ovo je blokirajuća stavka za potpuno samostalni deployment i mora se rešiti u kodu pre nego što se ZIP proglasi samostalnim.

5.6. PostgreSQL opcione promenljive

DATABASE_SSL
Gde: API okruženje.
Obavezno: NE za lokalni Compose PostgreSQL.
Koristi se kada je potrebna TLS veza sa udaljenom bazom.
Bezbednosna napomena: trenutni kod, kada je DATABASE_SSL=true, postavlja rejectUnauthorized=false. To znači da se ne proverava ispravnost sertifikata servera. Ovo nije idealno produkciono podešavanje; pre javne instalacije treba podržati proveru CA sertifikata.

PG_POOL_MAX
Gde: API okruženje.
Obavezno: NE.
Podrazumevano: 5 konekcija u pool-u.
Promena na novom serveru: prilagoditi samo ako kapacitet baze i broj API instanci to zahtevaju.

PORT
API_PORT
Gde: PORT obično dodeljuje hosting platforma; API_PORT je rezervni port za samostalno pokretanje.
U Compose konfiguraciji API_PORT je 4000.
Promena na novom serveru: ne izlagati API port javno kada Caddy treba da bude jedini javni ulaz.

NODE_ENV
Gde: Dockerfile i hosting okruženje.
Obavezno: produkciono okruženje treba da koristi production.
Promena na novom serveru: ne ostavljati razvojni režim na javnom serveru.

5.7. Administratorski TOTP — trenutno privremeno isključen

ADMIN_2FA_ENCRYPTION_KEY
Gde: API okruženje, kada se ponovo aktivira Google Authenticator/TOTP.
Obavezno: NE dok je dodatna potvrda isključena.
Očekivani format: tačno 64 heksadecimalna znaka.
Bezbedno generisanje: openssl rand -hex 32.
Promena na novom serveru: generisati novi ključ i čuvati ga u password manager-u i sigurnom backup-u. Gubitak ključa može onemogućiti dešifrovanje postojećih TOTP tajni.

Stanje:
- TOTP tabela, šifrovanje tajne, QR kodovi i rezervni kodovi postoje u API kodu/bazi.
- administratorski middleware trenutno ne zahteva TOTP;
- frontend je uklonio neaktivne Authenticator kontrole;
- dodatna potvrda je privremeno isključena po poslednjim commit-ovima od 08.11.2026.
- Ne prikazivati TOTP kao aktivnu zaštitu dok se ponovo ne uključi i end-to-end proveri.

APR_API_KEY

6. FOTOGRAFIJE I FAJLOVI
===============================================================================

Potvrđeno u standalone/api/server.mjs i standalone/db/init.sql:

- Najviše 7 fotografija po oglasu/zahtevu.
- Baza ima trigger koji sprovodi ograničenje od 7 fotografija.
- Prihvaćeni MIME tipovi: image/jpeg, image/png, image/webp.
- Maksimalna veličina ulaznog fajla: 20 MB po fotografiji.
- Sharp automatski primenjuje rotaciju prema EXIF-u, menja dimenzije na 800 x 600, koristi fit contain i belu pozadinu, a izlaz čuva kao JPEG uz kvalitet 82.
- Fotografije se povezuju sa ponudom ili zahtevom kroz slike_oglasa.
- API proverava vlasništvo oglasa i putanju fotografije.
- Administratorski API ima posebnu rutu za dodavanje fotografija na oglase.

Režimi skladištenja:
A) Bez S3/R2: sadržaj fotografije se čuva u PostgreSQL storage_objects.body (bytea). SQL backup zato obuhvata i nove fotografije.
B) Sa S3/R2: sadržaj fotografije se čuva u bucket-u, a PostgreSQL čuva vezu i putanju. Backup baze sam po sebi nije dovoljan; bucket mora posebno da se kopira.

Docker volumen uploads_data postoji i montira se na /data/uploads. U trenutnom kodu to nije jedino niti podrazumevano mesto za nove slike kada S3 nije podešen; nove slike idu u storage_objects. Volumen može biti potreban za legacy fajlove i statičke putanje.

Ne menjati putanju ili režim skladištenja na produkcionoj bazi bez plana za kopiranje fotografija i ažuriranje storage_path vrednosti.

7.3. Prijava i lozinke

- Backend za novu/reset lozinku zahteva najmanje 8 karaktera i najviše 72 bajta.

- javni feed ne treba da prikazuje pauzirane oglase;
- admin može eksplicitno da ih učita;
- vlasnički prikaz treba da ih zadrži u sopstvenoj evidenciji.

11. BEZBEDNOST, DOMEN, HTTPS I ODRŽAVANJE
===============================================================================

11.1. Domen i DNS

Za novi server:
1. Izabrati domen.
2. Kod DNS provajdera napraviti A zapis ka javnoj IPv4 adresi servera.
3. Ako se koristi IPv6, podesiti i odgovarajući AAAA zapis.
4. Proveriti da domen pokazuje na pravi server.
5. U standalone/.env postaviti DOMAIN na domen bez protokola.
6. PUBLIC_APP_URL postaviti na https:// i isti domen.
7. Omogućiti dolazni TCP 80 i 443; Caddy ih koristi za HTTP izazov i HTTPS.
8. Obezbediti da drugi servis ne zauzima portove 80/443.
9. Caddy automatski pribavlja i obnavlja sertifikat za javni domen.

Za lokalni test install.sh može koristiti :80 ili localhost; to nije javna HTTPS instalacija.

11.2. Firewall i pristup

- Javno izložiti samo 80/443.
- PostgreSQL port 5432 ne izlagati internetu.
- API interni port 4000 i frontend interni port 3000 ne izlagati ako Caddy služi kao jedini javni ulaz.
- SSH ograničiti na administratorske IP adrese gde je moguće.
- Redovno ažurirati Linux, Docker Engine i image verzije.
- Ne deliti Render SSH adresu, privatne ključeve ili .env.
- Obezbediti jaku jedinstvenu administratorsku lozinku.
- TOTP je trenutno isključen; to je privremeno slabija zaštita nego planirani konačni režim.

11.3. Zaštite u API kodu

Potvrđeno:
- Helmet zaglavlja
- bcrypt hash lozinki
- JWT HS256
- session_version za opoziv sesija posle promene lozinke
- rate limiting za prijavu, registraciju, reset lozinke, SMS i upload
- validacija ulaznih podataka
- provera vlasništva oglasa i fotografija
- ograničenje veličine i tipa upload fajlova
- javni kontakti se anonimizuju za neulogovane posetioce u odgovarajućim feed-ovima
- administratorske rute proveravaju administratorski identitet/ulogu

Ograničenja:
- TOTP enforcement je isključen.
- administratorska email adresa je delom hardkodirana u API kodu.
- CORS dozvoljene adrese su hardkodirane, ne čitaju se iz promenljive okruženja.
- DATABASE_SSL=true trenutno isključuje proveru sertifikata.
- browser API adresa je hardkodirana na Render API.
Sve ove stavke moraju biti razmotrene pre javne samostalne produkcije.

11.4. Režim održavanja

Administratorsko podešavanje se čuva u bazi. Tekst obaveštenja može se menjati. Pre javnog rada proveriti:
- da li se novi oglasi i registracije zaustavljaju;
- da li admin i dalje može da pristupi panelu;
- da li javni feed i detalji oglasa prikazuju odgovarajuću poruku;
- da li se stanje ispravno vraća nakon restarta API-ja.

11.5. Logovi i nadzor

Docker:
- docker compose ps
- docker compose logs -f api
- docker compose logs -f db
- docker compose logs -f web
- docker compose logs -f caddy

API provera:

Očekivani odgovor sadrži ok=true, database=connected i naziv baze. Ne smatrati samo HTTP 200 dovoljnim ako odgovor ne potvrđuje vezu sa bazom.

12. BLOKIRAJUĆA OTVORENA PITANJA ZA SAMOSTALNI ZIP
===============================================================================

Ovo su nalazi pregleda koda, ne izmena. Tokom ove provere nije menjan aplikacioni kod niti pokrenut deploy.

12.1. BLOKER 1 — Dockerfile.api ne kopira init.sql

Server:
standalone/api/server.mjs

Na kraju pokretanja servera API pokušava da učita:
path.resolve(__dirname, '../db/init.sql')

U Docker slici je server kopiran u /app/server.mjs, pa ta putanja odgovara /db/init.sql.

Aktuelni standalone/Dockerfile.api kopira:
- standalone/api/package.json
- standalone/api/server.mjs
- standalone/api/grant-admin.mjs

Ne kopira standalone/db/init.sql u /db/init.sql.

docker-compose.yml montira init.sql samo u PostgreSQL kontejner na /docker-entrypoint-initdb.d/001-init.sql, ne u API kontejner.

Zaključak:
Po statičkom pregledu, API Docker kontejner nema datoteku koju server pokušava da pročita i može da se ugasi pri pokretanju. Kompletan Docker build/run nije izvršen, pa se ovo označava kao vrlo verovatan blokirajući problem koji treba potvrditi testom i ispraviti pre ZIP isporuke.

12.2. BLOKER 2 — browser klijent koristi hardkodiranu Render API adresu

Putanja:
src/integrations/standalone/client.ts

Konstanta API_ORIGIN je hardkodirana na:
https://ponudimi-test-api.onrender.com

Browser deo api(), ensureApiReady() i storage.getPublicUrl() koristi tu adresu. API CORS trenutno dozvoljava:
- https://ponudimi-novo.onrender.com
- http://localhost:5173
- http://127.0.0.1:5173

Za novi domen browser bi i dalje pokušavao da poziva stari Render API, a novi domen nije u dozvoljenom CORS skupu.

Caddy već ima pravila da /api i /uploads prosleđuje lokalnom API servisu, ali browser klijent u trenutnom kodu koristi apsolutni Render URL i zato ne koristi nužno Caddy istog domena.

Zaključak:
Samostalna instalacija na drugom domenu nije potvrđena kao nezavisna od Render API-ja. Potrebna je promena API klijenta na bezbedno same-origin adresiranje ili potpuno konfigurabilan browser API URL, uz usklađivanje CORS pravila. Ne pokušavati produkcionu migraciju pre ove ispravke.

12.3. BLOKER 3 — promenljive za API adresu nisu usklađene

vite.config.ts čita PONUDIMI_API_ORIGIN i postavlja Nitro proxy pravila.
docker-compose.yml prosleđuje API_INTERNAL_URL web servisu.
standalone/client.ts koristi API_INTERNAL_URL samo u SSR putanji, dok browser putanja ostaje hardkodirana.

Zato promena samo PONUDIMI_API_ORIGIN ili API_INTERNAL_URL ne rešava browser pozive u trenutnom kodu. Potrebno je jedinstveno rešenje i test i u browser-u i u SSR-u.

12.4. NESLAGANJE DOKUMENTACIJE — email/SMS verifikacija

README-SR na API grani tvrdi da se novi nalog ne može koristiti dok se ne potvrde email i SMS.
Trenutni register/login kod vraća sesiju odmah i ne zahteva potvrdu.
Uskladiti README sa stvarnim stanjem ili ponovo uključiti verifikaciju kroz kontrolisanu promenu koda. Ne podešavati SMTP/Twilio kao navodno obavezne za prijavu dok je ovaj tok isključen.

12.5. NESLAGANJE DOKUMENTACIJE — fotografije

Neki README/.env opisi navode lokalni disk kao podrazumevano skladište.
Aktuelni API saveImage bez S3 konfiguracije upisuje binarne podatke u PostgreSQL storage_objects.
Glavni dokument prati ponašanje koda; README treba kasnije uskladiti.

12.6. NESLAGANJE DOKUMENTACIJE — prvi admin

README na main grani opisuje automatsko dodeljivanje admin uloge pri registraciji.
Aktivna API grana ima grant-admin.mjs i poruku da se uloga dodeljuje ručno na serveru.
Za trenutni API koristiti ručnu komandu grant-admin. README na main grani je zastareo za ovu proceduru.

12.7. Administratorski identitet

14. BACKUP, OBNOVA I ODRŽAVANJE PODATAKA
===============================================================================

14.1. Postojeće skripte

standalone/scripts/backup.sh
- pravi SQL dump PostgreSQL baze u standalone/backups;
- pravi tar.gz arhivu sadržaja /data/uploads;
- traži da se oba fajla kopiraju na drugu lokaciju.

standalone/scripts/restore.sh
- prima SQL backup i arhivu fotografija;
- traži potvrdu;
- vraća SQL u postojeću bazu;
- raspakuje fotografije u /data/uploads.

Primer:
./scripts/backup.sh

Primer obnove:
./scripts/restore.sh backups/ponudimi-db-DATUM.sql backups/ponudimi-fotografije-DATUM.tar.gz

14.2. Šta postojeći backup ne obuhvata

- S3/R2 bucket: mora se posebno kopirati.
- .env: ne kopirati u javni backup; sačuvati odvojeno u šifrovanom password manager-u ili sigurnom vault-u.
- caddy_data i caddy_config: nisu uključeni u postojeći backup; Caddy može ponovo pribaviti sertifikat, ali ovo nije potpuna kopija konfiguracije.
- Compose fajlovi i sam kod: čuvati u Git-u i u verzionisanoj ZIP arhivi.
- nema potvrđenog automatskog rasporeda backup-a.

14.3. Preporučena politika

- dnevni backup baze;
- dnevni backup fotografija ili S3 bucket-a;
- kopija van servera;
- šifrovanje backup arhiva;
- zadržavanje više dnevnih i nedeljnih verzija;
- periodični probni restore na zasebnu test bazu;
- pre svake migracije ili nadogradnje napraviti dodatni backup;
- nikada ne koristiti docker compose down -v kao rutinsku komandu, jer briše volumene.

14.4. Primer rasporeda

Kada je poznata stvarna putanja instalacije, cron može pokretati backup npr. svakog dana u 02:00:
0 2 * * * cd /ABSOLUTNA/PATH/DO/ponudimi/standalone && ./scripts/backup.sh

Ovo je primer, nije trenutno podešen cron. Putanju i korisnika treba prilagoditi stvarnom serveru. Cron rezultat treba slati u log i proveravati.
